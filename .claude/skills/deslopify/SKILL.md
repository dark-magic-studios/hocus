# Deslopify

Strips out "slop" — low-quality, repetitive, or boilerplate content generated by AI assistants. Use this skill when a file has been padded with unnecessary comments, redundant explanations, overly verbose docstrings, or filler text.

## When to use
- You notice excessive inline comments explaining what obvious code does
- A file has more comment lines than code lines
- Docstrings repeat the function signature in prose
- Generated code includes unnecessary imports, variables, or fallthrough cases
- README or docs have long-winded explanations that say nothing
- After merging an AI-generated PR: run deslopify before review
- Before committing: run deslopify on the diff to trim fat

## Instructions
1. **Identify slop patterns**
   - Comments that restate the obvious: `// increment i` next to `i++`
   - Docstrings that parrot parameter names and types: `@param name - The name`
   - Entire comment blocks that add zero signal for anyone who can read code
   - Redundant variable assignments: `const result = someFunc(); return result;` → `return someFunc();`
   - Unnecessary null/undefined guards on values that are guaranteed present
   - Boilerplate try/catch wrappers that all do the same thing (log + rethrow)
   - Generated test files with placeholder names (`test1`, `should work`) and no meaningful assertions
   - AI apology loops: "I should note that...", "It's worth mentioning...", "As previously stated..."

2. **Apply surgical removal**
   - Delete comments entirely unless they explain *why* (not *what* or *how*)
   - Collapse obvious indirection: inline single-use variables, flatten early-return chains
   - Remove generated "Example:" sections in code that have no educational value
   - Strip unnecessary blank lines between every logical block (one blank line max between sections)
   - Remove `eslint-disable`, `ts-ignore`, `prettier-ignore` that aren't actively needed
   - Remove log statements that were clearly for debugging and aren't actionable in production

3. **Tighten without breaking**
   - Prefer deletions over rewrites. If it compiles and reads fine with 10 lines removed, remove them.
   - Never remove error handling, validation, or safety checks — those aren't slop
   - Never remove content that a reader would genuinely need to understand a non-obvious piece of logic
   - Never remove JSDoc/TSDoc on public API surfaces consumed by other modules or teams
   - When in doubt, remove less. You can always trim more later.

4. **Verify after trimming**
   - The file still parses/compiles
   - The file still exports the same public API
   - Tests still pass (if applicable)
   - No stray punctuation, broken markdown, or orphaned section headings

5. **Report what you removed**
   - Provide a summary: "Removed X comment lines, Y redundant variables, Z blank lines"
   - If you skipped certain sections (e.g., left a docstring because it's a public API), note why
